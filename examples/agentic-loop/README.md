# agentic-loop

Two things at once: a workflow with an agentic turn in it, and — this README — the
authoring loop an agent walks over `flow mcp` to write one. The other examples show
what the language can express; this one shows how a machine with no filesystem, no
editor and no `flow` binary gets from "no file" to "a run in production".

The tool names below are the real ones, from
[`docs/reference/mcp.md`](../../docs/reference/mcp.md), which is generated by
walking the service descriptor. Every transcript here was produced by driving
`flow mcp` over stdio against the two files in this directory. The JSON is
pretty-printed and fields carrying nothing (`""`, `null`, an empty list the text
around it is not about) are elided; no value shown has been changed.

## The workflow

`workflow.yaml` is one bounded agentic turn against a model gateway, a cost ceiling
read off what the turn actually spent, a human gate crossed only when that ceiling
was, and the write that lands the result. Three decisions in it are the ones worth
copying, and `workflow.test.yaml` checks each rather than asserting it in prose:

- **A read is retried and the turn is not.** `brief` gets three attempts, because
  nothing on the far side changes when it runs twice. `turn` gets `attempts: 1`,
  because a retried agentic turn is a *new* turn: new cost, new nondeterminism, and
  for a turn permitted to write, possibly new writes.
- **The budget is written down once.** It is the gate's own `if:`; every later step
  asks `has(steps.review)` — whether the gate happened — rather than re-deriving why
  it would have.
- **A gate nobody answers denies.** The wait reports `timed_out` rather than failing,
  and the gate's `outputs:` shaping turns that into `approved: false` instead of a
  payload nobody sent.

## The loop

### 1. `flowstate_get_catalog` — what may a step name at all

Every task with its typed inputs and outputs, and every CEL function an expression
may call. It answers from this process's own registry, or, when the server was
started with `--address`, from the deployment that will actually run the file: a
worker with plugins loaded can run tasks this binary has never heard of, so
"what tasks exist" is a property of a deployment rather than of a laptop. Read it
before writing, not after a step fails with `unknown task`.

### 2. `flowstate_validate` — is this a file at all

Pure: reads nothing, writes nothing, starts nothing, so it is the one tool in the
loop that can be hammered unattended. A draft with `wait_for_signals:` in it:

```json
{"report": {"files": [{"file": "workflow.yaml", "diagnostics": [
  {"line": 113, "column": 5,
   "message": "unknown key \"wait_for_signals\"; did you mean \"wait_for_signal\"?",
   "step": "review", "code": "general",
   "edits": [{"title": "rename to `wait_for_signal`",
              "changes": [{"range": {"startLine": 113, "startColumn": 5,
                                     "endLine": 113, "endColumn": 21},
                           "newText": "wait_for_signal"}]}]}]}]}}
```

Position, suggestion, and a range to apply — an agent edits from `edits` rather than
from the sentence, and `code` is what program logic branches on, because the prose is
explicitly allowed to be reworded.

What it will not tell you is whether the file *does* the right thing. A workflow that
computes the wrong number validates perfectly.

### 3. `flowstate_test` — does it behave

The tool this example exists to argue for. It runs `workflow.test.yaml` against
`workflow.yaml` as two submitted strings, through the identical machinery `flow test`
runs on two files:

```json
{"file": "<submitted>", "cases": [
  {"name": "a turn inside its budget lands with nobody asked", "passed": true, "failures": [], "duration": "0.007508600s"},
  {"name": "a turn over its budget lands only once a person answers", "passed": true, "failures": [], "duration": "0.009292557s"},
  {"name": "the same turn does not land when the gate goes unanswered", "passed": true, "failures": [], "duration": "0.005760094s"}],
 "refused": ""}
```

A few milliseconds for a case whose gate waits twenty-four hours: time is virtual, and
`at: 2h` in the second case is a signal arriving two hours in. Note also that every
effectful step is stubbed, which is what makes the whole of this reachable with no
network, no gateway, no credential, and no operator opt-in — a stubbed run never
invokes a real task, so there is nothing for an egress policy to govern.

A case that fails answers with its unmet expectations as positioned diagnostics; a
case that never reached a verdict at all says why in `error` instead.

### 4. `flowstate_run_local` — what happens when something real is on the other end

Same file, no stubs:

```json
{"run": {"status": "STATUS_FAILED", "error": {
  "message": "step \"brief\": task \"http\": Get \"https://tracker.internal.example.com/issues/241\": denied by egress policy: https://tracker.internal.example.com/issues/241 (deny rule: true)",
  "kind": "PolicyDenied"}}}
```

`isError: true` on the tool result, so a model cannot mistake this for a run that
worked, and `error.kind` says `PolicyDenied` as a value rather than as a sentence:
the agent branches on it — repair the file, retry, or tell the operator — without
parsing prose. This one means *tell the operator*. `flow mcp` denies egress and
registers no secret scheme unless it was started with `--egress-policy`,
`--secret-env`, `--secret-dir` or `--auth-policy`, and nothing a client sends can
widen that.

Which is the whole reason step 3 comes before step 4 rather than after it. Under a
server with no opt-in, every rehearsal of a workflow that touches the network dies
here, and an agent with only this tool can prove its file parses and nothing else.
Reach for `flowstate_test` while authoring, and for `flowstate_run_local` afterward,
to rehearse the real effect of whichever task you deliberately left unstubbed.

### 5. `flowstate_run`, `flowstate_signal`, `flowstate_get` — the durable half

These need a server (`flow mcp --address ...`); the four above do not, and neither
does `flowstate_compile`, which turns the source into the specification
`flowstate_run` takes. `flowstate_run` submits it and answers with a run id.
`flowstate_signal`
delivers `turn-approved` to a waiting gate — this run's `workflowId`, the name from
`wait_for_signal:`, and `payload.namedValues.approved` set to a boolean literal.
`flowstate_get` reads back the same document `flowstate_run_local` answered with
above: status, timing, and step outputs, bounded so a long run's transcript is
reduced to something that still parses rather than refused.

The rehearsal proved this file's conditions, its retry policies and its data flow.
It proves nothing about durability, and nothing about whether the gateway behaves
the way a stub's `returns:` said it would.

## Running it yourself

```console
$ flow test examples/agentic-loop/
PASS  examples/agentic-loop/workflow.test.yaml: a turn inside its budget lands with nobody asked
PASS  examples/agentic-loop/workflow.test.yaml: a turn over its budget lands only once a person answers
PASS  examples/agentic-loop/workflow.test.yaml: the same turn does not land when the gate goes unanswered
examples/agentic-loop/workflow.test.yaml  6/6 steps reached
```

That is the same run `flowstate_test` performs, on files instead of strings, and it
is what CI runs over this directory.

`flow run local examples/agentic-loop/workflow.yaml` needs a model gateway and a
tracker at the two hosts its `http:` steps name — neither of which exists — so it
fails at the first step, with DNS rather than with a policy:

```console
$ flow run local examples/agentic-loop/workflow.yaml
running locally
this workload waits for signal "turn-approved", which nothing here will send; it will block until that wait times out
  to answer it now:  --signal turn-approved='{"approved": true}'
ERROR
error running workflow locally: step "brief": task "http": Get
"https://tracker.internal.example.com/issues/241": dial tcp: lookup
tracker.internal.example.com on 8.8.8.8:53: no such host
```

The two failures are worth putting side by side: the command a person runs on their
own machine reaches the network by default, and the MCP surface an agent drives does
not. Same file, same engine, different answer — because one of them is deciding what
an untrusted caller may reach.
